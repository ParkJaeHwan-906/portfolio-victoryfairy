    요청 경로

    CloudFront 단일 진입점 · FE 요청은 ALB 를 거치지 않음

    FE 응답 실측 77ms 엣지에서 정적 반환
    API 응답 실측 58~93ms quiz 58ms · user 93ms
    엣지 → ALB → 파드
    FE 요청이 거치는 파드 설계값 0개 nginx 파드를 제거했습니다
    ALB 도 거치지 않습니다

    CloudFront가 유일한 진입점입니다. 경로를 보고 정적 자산은 S3에서, API는 ALB 뒤의 EKS 파드에서 가져옵니다. 갈림이 CloudFront에서 일어나므로 FE 요청은 ALB에 닿지 않습니다.

    FE와 API를 같은 오리진에 두기 위해서입니다. API를 api.victoryfairy.com으로 빼면 CORS·프리플라이트가 따라오고 번들에 절대 URL을 구워야 합니다. 경로로 갈라 보내면 프런트는 /api/auth/login처럼 상대 경로만 알면 됩니다.

    요청 경로 시연

    세 경로가 갈리는 지점은 CloudFront behavior 하나입니다. FE 를 실행하면 ALB 와 파드가 한 번도 켜지지 않습니다.

    전환 전후 비교

    혼동하기 쉬운 지점입니다. 예전에는 ALB가 인터넷의 첫 관문이었고 FE도 그 뒤의 nginx 파드에서 나왔습니다. 지금은 CloudFront가 최상단이고 ALB는 그 오리진 중 하나입니다.

    CloudFront behavior 정책

    경로오리진엣지 캐시브라우저메서드압축
    /assets/*S31년immutableGET·HEADon
    그 외S30초no-cacheGET·HEADon
    /api/*ALB없음—7종 전부off
    /rt/*ALB없음—7종 전부off

    메서드 7종. behavior의 기본 허용은 GET, HEAD뿐입니다. 그대로 두면 로그인·회원가입 등 모든 POST가 405로 막힙니다.

    API는 캐시 없음. 엣지가 API 응답을 담으면 한 사용자의 응답이 다른 사용자에게 노출됩니다. Authorization 헤더는 오리진까지 그대로 전달합니다.

    /rt/*는 압축 끔. SSE가 엣지에서 버퍼링될 여지를 만들지 않는 쪽을 택했습니다.

    SPA 딥링크 처리

    /login처럼 서버에 실재하지 않는 경로는 CloudFront Function이 /index.html로 재작성합니다. custom error response(404 → index.html)로 하지 않은 이유가 있습니다. 그 설정은 behavior 단위가 아니라 distribution 전역이라, API가 정상적으로 반환한 404·403까지 HTML + 200으로 바꿔버립니다.

    같은 이유로 /assets/*에는 함수를 붙이지 않습니다. 붙이면 없는 청크 요청이 index.html로 200 응답돼 Unexpected token '<'로 번집니다.

    Ingress 구성: 세 개가 ALB 하나를 공유

    헬스체크 경로가 앱마다 달라(/api/actuator/... vs /rt/actuator/...) Ingress를 분리했습니다. 그 어노테이션은 Ingress 단위라 하나로는 두 값을 담을 수 없습니다. 대신 group.name을 같게 주어 ALB는 하나로 유지하고, group.order로 리스너 규칙 평가 순서를 고정합니다.

    ALB의 헬스체크는 /actuator/health 전체가 아니라 readiness 그룹을 봅니다. 전체 health는 DB·Redis 인디케이터를 합산해 DOWN을 내므로, MySQL EC2가 일시적으로 불안정해지면 멀쩡한 파드까지 타깃에서 빠져 전면 503이 됩니다.

    세 번째 Ingress victoryfairy-dns-origin은 라우팅이 목적이 아닙니다. origin.victoryfairy.com을 ExternalDNS에 알리는 것이 유일한 역할입니다. Terraform은 LBC가 만든 ALB의 주소를 알 수 없어 그 레코드를 대신 만들 수 없습니다.

    기획이 어떻게 바뀌었고, 그래서 무엇을 골랐나

    v1 은 응원 구단별로 늘 열려 있는 방이었습니다. v2 에서 기획이 그날 경기를 함께 보는 사람들의 하루짜리 방으로 바뀌었습니다. 방은 경기마다 매일 새로 열리고, 응원 팀과 상관없이 누구나 들어오며, 다음 자정이 지나면 대화가 남지 않습니다. 이 기획에서 나온 요구와 각각에 맞춰 고른 설계를 짝지었습니다.

    영역바뀐 기획이 요구하는 것그래서 v2 에서는
    방 단위같은 경기를 보는 양 팀 팬이 한 방에서 이야기합니다. 방은 경기마다 그날 하루만 존재합니다.오늘 경기 단위로 방을 엽니다. 00:00 KST 에 그날 경기로 방을 만들고 로그인 사용자 누구나 들어옵니다.
    저장대화는 다음 자정에 사라집니다. 영구 저장소가 필요 없고, 탈퇴자 메시지를 옮겨 둘 이유도 없습니다.RDB 에 저장하지 않습니다. 원문은 Kafka 에 48시간, 조회용 사본은 Redis Stream 에 하루만 둡니다. 방 키 TTL 로 자정에 함께 사라져 이관 로직도 필요 없습니다.
    쓰기 경로DB 가 빠지면 전달과 히스토리가 같은 원본에서 나와야 둘이 어긋나지 않습니다.쓰기 지점을 Kafka 하나로 둡니다. 전달과 히스토리 저장은 그 로그를 읽는 소비자가 각자 맡아, 둘 중 하나만 성공하는 상태가 생기지 않습니다.
    끊긴 구간경기 중 대화는 그 순간의 장면을 두고 오갑니다. SSE 가 끊긴 사이(30분 타임아웃·파드 재시작·네트워크) 들어온 메시지를 이어서 돌려줘야 합니다.Kafka 로그 + Stream 사본으로 복구합니다. 재접속 때 Last-Event-ID 이후를 Stream 에서 먼저 채운 뒤 실시간에 합류시킵니다.
    중복전송은 Kafka 적재만 확인하고 바로 답합니다. 응답을 못 받은 클라이언트가 재시도해도 같은 메시지가 두 번 생기면 안 됩니다.메시지마다 clientMsgId 를 받아 멱등 키로 씁니다. 같은 키가 다시 오면 처음과 같은 202 와 msgId 를 돌려줍니다.

    관리형 데이터베이스는 인스턴스 요금에 관리형 요금이 추가됩니다. 이 규모에서는 그 차이가 프로젝트가 감당할 수 있는 선을 넘었고, 데이터 계층이 전체 비용에서 가장 큰 항목이었습니다. 다른 이유는 없습니다. 기술적으로 RDS 가 부족해서 내린 결정이 아닙니다.

    데이터 보존: EBS 와 S3 이중화

    Blue/Green 무중단 롤아웃

    BE 롤아웃은 maxSurge: 100% / maxUnavailable: 0으로 두었습니다. 이 두 값이 파란(현행)과 초록(신규)이 한동안 함께 떠 있는 상태를 만듭니다.

    • maxUnavailable: 0 — 옛 파드를 하나도 먼저 내리지 않습니다. 전환 중에도 현행 용량이 100% 유지됩니다.
    • maxSurge: 100% — 신버전을 현재 replica 수만큼 한 번에 띄웁니다. 부분 교체가 아니라 한 세트를 새로 세웁니다.

    신버전 세트를 전부 띄우고 검증을 통과한 뒤에 트래픽을 옮깁니다. 옮기기 전까지 초록 세트는 요청을 받지 않으므로, 전환 전후로 서비스 용량이 달라지지 않습니다. 통과하지 못하면 전환이 진행되지 않고 옛 파드가 계속 요청을 받습니다. 실패한 배포가 장애가 되지 않으며, 그 상태에서 rollout undo로 되돌립니다.

    전환 순간에는 파드가 두 배로 떠 있습니다. 초록 세트를 전부 띄운 상태에서 파란을 곧바로 지우지 않고 롤백 대상으로 남기기 때문입니다. 피크에 replica 가 올라가 있으면 그 몫은 Cluster Autoscaler 가 임시로 늘립니다.

    하위 호환되지 않는 스키마 변경은 이 방식만으로 안전하지 않습니다. 되돌릴 수 있어야 의미가 있는 구성인데, 컬럼을 지우거나 이름을 바꾸면 파란으로 되돌리는 순간 옛 코드가 새 스키마를 만납니다. 그런 변경은 두 번에 나눠 배포합니다.

    장수명 연결도 함께 봅니다. 전환하면 파란 세트가 타깃그룹에서 빠지므로, 그 파드에 붙어 있던 채팅 SSE 스트림은 드레이닝이 끝나는 시점에 끊기고 클라이언트가 다시 연결합니다. 스트림은 파드에 붙어 있어 다른 파드로 이전되지 않습니다.

    인증이 없는 쓰기 경로는 곧 누구나 S3 에 객체를 만들 수 있는 경로입니다. 요청 한 번이 객체 하나이고, 가입으로 이어지지 않은 객체는 저장 비용과 정리 비용으로 남습니다. 그래서 클라이언트가 발급한 appId 를 키로 Redis 카운터를 두고, 한 창 안에서 10회까지 허용하고 11번째를 429 로 거절합니다. 사진을 바꿔 보는 정상 사용자에게는 충분하고, 같은 식별자로 반복 호출하는 스크립트는 객체를 만들기 전에 여기서 멈춥니다.

    판정 순서가 계약입니다

    식별자 확인 → 이미지 검증 → 카운터 증가 → 저장. 이 순서에서 어느 단계가 어느 단계보다 앞인지가 각각 하나의 결정입니다.

    • 판정은 증가 결과로 합니다. "지금 몇 회인지" 읽고 나서 더하면 동시 요청 둘이 각각 9회를 읽고 나란히 통과합니다. INCR 의 반환값으로 판정해 게이트를 원자적으로 잡았습니다.
    • 창은 고정입니다. TTL 은 키가 새로 생길 때 한 번만 겁니다. 증가할 때마다 갱신하면 30분 안에 계속 올리는 사용자는 창이 끝나지 않아 영영 갇힙니다.

    환불: 저장 실패분만 되돌립니다

    증가가 저장보다 앞이면 S3 장애가 정상 사용자의 슬롯을 태웁니다. 저장 실패 10회가 한 식별자의 한도를 조용히 소모하는 것이 실측됐습니다. 순서를 "저장 성공 후 증가"로 바꾸면 판정과 증가 사이에 창이 생겨 동시성 방어가 무너지므로, 순서는 그대로 두고 실패한 회차만 환불했습니다. 한도 초과 거절은 환불하지 않습니다. 이미 넘긴 창의 값이 11, 12 로 늘어도 판정은 같고 TTL 도 밀리지 않습니다.

    환불은 단순 DECR 로 하면 안 됩니다. Redis 의 DECR 는 키가 없으면 -1 로 새 키를 만들고, 그 키에는 TTL 이 없습니다. 창이 끝나 키가 사라진 뒤 도착한 실패 요청 하나가 영구 키를 남기면 그 식별자는 사실상 무제한이 됩니다. 존재 확인·감소·0 하한을 Lua 스크립트 하나에 묶어 원자적으로 처리했습니다.

    환불 자체는 best-effort 입니다. 환불이 실패해도 예외를 올리지 않고 로그만 남깁니다. 여기서 예외를 던지면 저장 실패(원인)가 환불 실패(결과)에 가려집니다. 최악의 결과는 그 식별자가 슬롯 하나를 잃는 것뿐이고, 창이 30분이라 저절로 회복됩니다.
